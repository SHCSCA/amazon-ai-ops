# V1.6 发布与真实运行规格

> 2026-10-27 文档对齐：本文定义合同、方法或验收案例，不提供当前通过结论。现行状态、失败与后续计划统一见 [项目状态](PROJECT_STATUS.md)；当前仍为 APP_NEEDS_WORK / INTERNAL NON_READY。正文中的旧检查点只适用于当时版本。

版本：1.0；状态：待实测。以完整 PRD 172 MUST 与 L1–L8 为验收范围，不继承旧 READY。

## 候选冻结

完成 L1–L5 软件验收后冻结源码树摘要、依赖锁文件、安装 EXE、便携 EXE、ZIP、解包应用内容与 Main bundle。候选内容/合同改变即重算身份并重跑受影响证据，不能只改报告中的哈希。

## 双店运行

- 两个真实 US 店铺，各自独立 StoreId、BrowserProfileId、ERP/Ads 账户映射、sessionGeneration，America/Los_Angeles 业务日期和 USD。
- 按美国已完成业务日统计，每店至少七个完整日；记录日期边界、原始报表、同一根任务的 exact 8/8 导入、分析、决策与运行事件。两个店的事件不得互相补齐。
- 日期不足、缺报表、模板未知、登录过期、旧会话响应、A→B→A、过期竞价或对象不唯一，记录中文原因并按真实恢复路径处理。
- 只读验收须证明无业务写入；正式导入/迁移/执行按允许变化对账。

## 两种真实执行

人工模式和策略自动模式分别使用自然产生的完整合格候选、Decision、Grant、批次、任务及独立证据，不能裁剪不合格建议制造通过。

人工模式须由用户在产品内批准具体候选。策略模式由当前启用策略和生产策略运行时授权，无人工补签。两者均只允许关键词 lower_bid，降幅不超过 min(10%, Grant 上限)，绑定当前 Profile/会话/对象/竞价/修订。

提交意图先持久化，每动作最多一次提交；保留 before、after、独立刷新 readback。断线/崩溃后的 UNKNOWN 只读对账，不重试旧提交、不恢复旧 Grant、不作为效果证明。急停、重复点击和策略变更通过反向测试及适用的真实只读演练验证。

执行证据使用 `mission-control-execution-canary-evidence/v2` 与 `mission-control-execution-canary-authority/v2`，由现有导出器和 readiness verifier 共同调用 `verifyExecutionCanaryLineage` 校验。缺少不可变 authority snapshot 的旧 v1 记录不能补默认值获得当前资格。校验固定完整 action batch、完整 StoreContext、模式修订和单一 issuer；Mission 通过连续历史从签发修订推进，Decision 通过 approved→executed→verified 历史推进。一次 durable intent 必须对应唯一 job、reserved/spent slots 与相邻 intent_written/submitted 事件；consumed 由实际提交发生，须早于后续截图。Grant 有效期在提交时检查，提交后的到期不否定已发生且有证据的事实，也不允许额外提交。来源、数据库、包体、截图哈希和最终快照时效仍由原严格检查验证。

实验基线引用已验证 Decision 的固定分析对象 authority；后续对象修订不能替换基线。结果引用新完整八报表批次的最新对象修订，拒绝回退旧导入；八份对账、准确窗口与美国已完成业务日均须满足。只有系统测量与护栏判定才能产生结论和记忆证明，测试采集/AI/浏览器输入只计隔离 L3，不能计双店或真实执行。

## 性能、成本与无障碍

正式发布的性能与成本验收先记录典型和最大支持样本的行数、任务数、内存、启动时间、页面/IPC 延迟 p50/p95、导入时间、模型调用次数/令牌/实际成本、超时及重用。提出独立预算给用户确认，再按批准预算重新验收；实测数值本身不是合格阈值。开发侧内部工程阈值的定义审查和软件实测比较不代替上述用户批准、AI费用原件或正式日窗口观察。

实包覆盖 100%、125%、宽屏和最小窗口，六模块22入口、弹窗/焦点/键盘/缩放/错误恢复。记录自动检查与人工可用性证据的区别。

## 最终交付

源码版本与未提交树摘要、安装/便携/ZIP、SHA-256 清单、迁移恢复和操作指南、完整验收报告、匹配 READY bundle。仅全部 MUST 与 L1–L7 当前通过时 L8 可输出 APP_READY；缺少第二店登录、验证码、人工候选批准、七日观察或预算确认时保留可恢复候选与具体阻断。
